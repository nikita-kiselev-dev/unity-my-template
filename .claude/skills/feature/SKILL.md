# Feature — проектирование фичи до кода

Режим **проектирования**. Один вызов = одна фича, доведённая до тикета, готового к реализации в **другой** сессии.

Общие правила проекта — `AGENTS.md`. Ответы — на русском, без эмодзи.

## Жёсткое ограничение режима

- **Не писать код.** Никаких правок в `Assets/`, `Tools/`, `ProjectSettings/`. Не запускать тесты, не собирать генератор.
- Разрешено **только чтение** кода и доков (`Read`, `Grep`, `Glob`, read-only `Bash`).
- Единственный файл на запись — **тикет** в `unity-my-template-docs/Tasks/Features/`.
- Сессия заканчивается стоп-гейтом (см. ниже). Не переходить к реализации, даже если пользователь скажет «ну давай уже делай» — предложить открыть новую сессию.

Почему так: агент, который знает, что через минуту будет писать код, думает в терминах «как сделать», а не «что сделать», а написав код — защищает своё решение вместо того, чтобы его критиковать. Разделение фаз — не бюрократия, а условие, при котором вообще появляются нетривиальные варианты. Не «оптимизировать» это ограничение прочь.

## Фаза 0 — Проблема, а не решение

Пользователь почти всегда приходит с решением. Признаки: в запросе есть имена файлов, классов, папок; глаголы «сделай / добавь / вынеси / перенеси»; название паттерна.

Развернуть обратно к проблеме и показать пользователю три строки:

```
Сейчас: <что происходит / чего нет>
Хочу:   <какой наблюдаемый результат нужен>
Почему: <зачем это игроку или проекту>
```

Плюс **критерий Done** — проверяемый, до разведки. «Работает» не годится; годится «при клике по кнопке X валюта растёт на N, попап закрывается, тест Y зелёный».

Правила фазы:

- Если переформулировка меняет смысл — спросить, что верно. Один вопрос, не анкета.
- Если пользователь говорит, что решение уже принято и обсуждать нечего — зафиксировать его как **входное ограничение**, а не как проблему, и идти дальше. Не спорить дважды.
- Названные пользователем файлы **не подставлять в постановку**. Они пригодятся в фазе 1 как подсказка, куда смотреть, но не как граница поиска.

## Фаза 1 — Разведка (read-only)

Цель — построить модель системы, а не найти три файла. Без этой фазы архитектурных вариантов не будет: предложить переиспользование можно только зная, что уже есть.

1. `unity-my-template-docs/01-Agent-Navigation.md` → релевантные статьи → секции `Для агента`, `Инварианты`, `Как расширять`.
2. Код по существу задачи. Обязательно посмотреть **шире названных пользователем файлов**: есть ли в `Foundation/` механизм, закрывающий часть задачи.
3. Сверить доки с кодом. Код — источник истины; расхождение зафиксировать.

Вывести карту:

```
## Как устроено сейчас
<механизм, участники, поток данных — коротко>

## Где похожее уже решено
<фича/сервис + чем именно похоже + можно ли переиспользовать>

## Инварианты, которые задену
<правила из AGENTS.md и доков, релевантные именно здесь>

## Что сломается или потребует правок
<файлы, тесты, сериализованные данные, Addressables>

## Чего в проекте нет
<явно: механизма X нет, придётся заводить>
```

**Гейт.** Спросить у пользователя, верна ли карта, и дождаться ответа. Ошибка понимания, пойманная здесь, стоит минуту; та же ошибка после реализации — часы.

## Фаза 2 — Варианты с ценником

2–3 варианта. Для каждого — полный ценник, иначе пользователь не сможет выбрать:

```
### Вариант N: <название>
- Суть: <1–2 предложения>
- Чем платим: <сложность, связность, производительность, новая зависимость>
- Если не делать: <что будет через 3 месяца>
- Цена отката: <дёшево / придётся мигрировать сейвы / переписать фичу>
- Прецедент: <где в проекте уже так сделано, или «прецедента нет»>
```

Правила, без которых фаза вырождается в банальщину:

- **Фильтр очевидности.** Вариант, до которого пользователь дошёл бы сам за минуту, идёт только как базовая линия. К нему обязателен минимум один вариант, требующий знания стека (VContainer, R3, UniTask, MemoryPack, source generator), архитектурного паттерна или чужого опыта.
- **Одна вещь, о которой не спрашивали.** Назвать минимум один фактор, который пользователь не поднимал, но который меняет решение: риск на мобилках, миграция сейва, порядок инициализации, стоимость в кадре, тестируемость.
- **Не выдумывать.** Если нетривиальных вариантов действительно нет — сказать это прямо и обосновать, почему задача одновариантная. Придуманная альтернатива хуже её отсутствия.
- **Рекомендация обязательна.** Не выкладывать варианты без выбора — назвать лучший и почему.
- **Возражать один раз.** Если пользователь выбрал вариант, который ты считаешь хуже, — сказать одной фразой, что именно проиграет. Пользователь настоял — выполнять его выбор без дальнейших споров.

## Фаза 3 — Тикет

`unity-my-template-docs/Tasks/Features/UMT-Feature-N.md`: скопировать канон
`Tasks/Features/UMT-Feature-1.md`, `N` — максимальный существующий номер + 1 (номер 1 не занимать).
Frontmatter: `status: Todo`.

Секции:

- **Цель** — одно предложение.
- **Проблема** — три строки из фазы 0.
- **Выбранное решение и почему** — вариант + аргумент выбора.
- **Отвергнутые варианты** — по одной строке с причиной. Нужно, чтобы через месяц не переоткрывать закрытый спор.
- **Скоуп** — чеклист атомарных проверяемых пунктов.
- **Вне скоупа** — что явно не делаем.
- **Тесты** — какие Model/VM/утилиты покрываем красными тестами до реализации; что не тестируем и почему.
- **Критерии Done** — проверяемые.
- **Открытые вопросы** — если остались.
- **Ручные шаги пользователя** — Unity-действия, если предвидятся.

## Стоп-гейт

Закончить ровно так:

```
Тикет UMT-Feature-N готов. Реализацию начинай новой сессией:

Реализуй UMT-Feature-N
```

Чистый контекст на реализации — часть смысла: агент прочитает тикет как постановку, а не как продолжение спора о вариантах.
