# Skills

## Для агента

Открывай эту статью, когда пользователь вызвал `/feature` или `/prompt-engineer`, когда нужно
понять, стоит ли предложить скилл, или когда заводишь новый.

Скиллы лежат в `.claude/skills/<name>/SKILL.md` и вызываются как `/<name>`. Их два, и оба —
**режимы с запретом на исполнение**: они заканчиваются артефактом (тикет или текст промпта), а не
изменённым кодом.

## Формат SKILL.md

Файл — обычный markdown с YAML-frontmatter из двух полей:

```markdown
---
name: feature
description: "Проектирование фичи до кода: ... Заканчивается готовым тикетом и стоп-гейтом."
---

# Feature — проектирование фичи до кода
...
```

`name` совпадает с именем папки и с тем, что пользователь набирает после слэша. `description` —
единственное, что видит агент до вызова: по нему решается, подходит ли скилл под запрос. Поэтому
описание пишется через **триггер и результат** («проектирование до кода… заканчивается тикетом»),
а не через список возможностей.

Тело — инструкции агенту на время работы скилла. Общие правила проекта в них не дублируются: оба
скилла ссылаются на `AGENTS.md` одной строкой.

Устойчивая структура обоих скиллов: заголовок с назначением → **жёсткое ограничение режима** →
процедура по фазам → формат выхода → стоп-условие.

## /feature — проектирование фичи

Один вызов = одна фича, доведённая до тикета, готового к реализации в **другой** сессии.

**Ограничение режима.** Код не пишется вообще: никаких правок в `Assets/`, `Tools/`,
`ProjectSettings/`, никаких прогонов тестов и сборок генератора. Разрешено чтение и ровно один файл
на запись — тикет в `unity-my-template-docs/Tasks/Features/`.

**Фазы:**

| Фаза | Что делает | Выход |
| --- | --- | --- |
| 0. Проблема | разворачивает решение обратно в проблему | три строки «Сейчас / Хочу / Почему» + критерий Done |
| 1. Разведка | строит модель системы, read-only | карта: как устроено, где похожее решено, какие инварианты задену, что сломается, чего в проекте нет |
| 2. Варианты | 2–3 варианта с полным ценником | суть, чем платим, если не делать, цена отката, прецедент |
| 3. Тикет | фиксирует решение | копия `UMT-Feature-1` → `UMT-Feature-N` со `status: Todo` |

**Два гейта.** После фазы 1 скилл спрашивает пользователя, верна ли карта, и **ждёт ответа**:
ошибка понимания, пойманная здесь, стоит минуту, та же ошибка после реализации — часы. В конце —
стоп-гейт: сессия заканчивается фразой «реализацию начинай новой сессией», и переход к коду не
делается, даже если пользователь просит.

**Почему фазы разделены.** Агент, который знает, что через минуту будет писать код, думает в
терминах «как сделать», а не «что сделать»; написав код — защищает своё решение вместо того, чтобы
его критиковать. Разделение — условие появления нетривиальных вариантов, а не бюрократия. В самом
скилле стоит явный запрет «оптимизировать» это ограничение прочь.

**Что делает фазу 2 не банальной** (это самая ценная часть скилла и первое, что деградирует при
правках):

- **фильтр очевидности** — вариант, до которого пользователь дошёл бы сам за минуту, идёт только
  как базовая линия; к нему обязателен вариант, требующий знания стека или паттерна;
- **одна вещь, о которой не спрашивали** — фактор, который пользователь не поднимал, но который
  меняет решение (миграция сейва, порядок инициализации, стоимость в кадре, тестируемость);
- **не выдумывать** — если задача одновариантная, так и сказать; придуманная альтернатива хуже её
  отсутствия;
- **рекомендация обязательна** — варианты без выбора не выкладываются;
- **возражать один раз** — пользователь настоял, скилл выполняет его выбор без повторных споров.

Тикет из фазы 3 богаче обычного скелета feature-тикета из [[Tickets]]: в нём есть «Выбранное
решение и почему» и **«Отвергнутые варианты»** — чтобы через месяц не переоткрывать закрытый спор.

## /prompt-engineer — постановка задачи

Превращает сырую формулировку пользователя в структурированный промпт для агента этого проекта.
Задача при этом **не исполняется**: единственный артефакт — текст промпта в одном код-блоке, чтобы
его можно было скопировать целиком.

Процедура: понять намерение (тип задачи, целевой исполнитель, затронутые области) → найти пробелы
(1–3 точечных вопроса, если они блокирующие; иначе дефолт плюс явное допущение) → откалибровать
объём (тривиальная правка не раздувается до полного шаблона) → собрать промпт по шаблону
(Задача / Контекст / Скоуп / Вне скоупа / Ограничения / Критерии успеха / Режим) → приписать
заметки промпт-инженера отдельно от код-блока.

Два правила наполнения, ради которых скилл и существует: **altitude** (задавать «что» и критерий,
а не диктовать реализацию построчно) и **точечные ограничения** (включать только те правила
`AGENTS.md`, которые легко нарушить именно здесь, — свод агент и так читает).

Имена типов, которые скилл подставляет в промпт, ничем машинно не проверяются: markdown вне
сборок не видят ни компилятор, ни `naming-check`. Переименование в коде обязано доезжать до
`SKILL.md` вручную — иначе скилл молча выдаёт постановку с несуществующими идентификаторами
(так уже было: скилл выдавал постановку с именами, которых в коде уже не было).

## Когда скилл, когда хук, когда AGENTS.md

Три механизма, и они не взаимозаменяемы:

| Механизм | Природа | Когда применим |
| --- | --- | --- |
| `AGENTS.md` | правило, которое агент читает всегда | общий свод, дефолтное поведение |
| Скилл | **процесс**, который нужно вызвать | последовательность фаз с гейтами, применимая не к каждой задаче |
| Хук | **гейт**, который нельзя обойти | инвариант, обязательный на каждом ходу |

Ключевое различие: **скилл можно не вызвать, хук не обойти**. Поэтому правило, которое обязано
выполняться всегда, живёт в хуке ([[Hooks]]), а не в скилле; а процедура, у которой есть моменты
ожидания ответа пользователя, — в скилле, потому что хук диалог вести не умеет.

`AGENTS.md` при этом остаётся дефолтом: если поведение нужно всегда и его не надо проверять
машинно, оно просто описывается там.

Практическое следствие для агента: если пользователь ставит задачу сразу решением («сделай X в
файле Y»), это можно выполнять как есть — но пространство решений закрыто, и архитектурных
альтернатив не будет. Когда задача этого стоит, `/feature` предлагается явно.

## Инварианты

- Каждая папка в `.claude/skills/` содержит `SKILL.md` с непустыми `name` и `description`.
- `name` во frontmatter совпадает с именем папки.
- Оба существующих скилла — read-only-режимы: они перечисляют разрешённые инструменты и явно
  запрещают правки кода.
- Скилл заканчивается стоп-условием, а не переходом к реализации.
- Скилл не дублирует `AGENTS.md`, а ссылается на него.
- Тикет, созданный `/feature`, проходит `ticket-format.ps1` — скилл не освобождает от конвенции
  [[Tickets]].

## Как завести новый скилл

1. Папка `.claude/skills/<name>/` и `SKILL.md` с frontmatter `name` + `description`.
2. `description` — триггер и результат: по нему решается, вызывать ли скилл вообще.
3. Первым разделом после назначения — **ограничение режима**: что скиллу запрещено. Без него скилл
   растворяется в обычной работе агента.
4. Процедура по фазам, у каждой — проверяемый выход. Фаза без выхода не проверяется и будет
   пропущена.
5. Стоп-условие: чем именно заканчивается вызов.
6. Строка в [[00-Index]] и в этой статье.

Перед тем как заводить: скилл нужен, когда есть **последовательность с гейтами**. Одно правило
скиллом не оформляют — ему место в `AGENTS.md`; обязательную проверку не оформляют скиллом — ей
место в хуке.

## Когда обновлять

- Добавлен или удалён скилл в `.claude/skills/`.
- Изменился состав фаз `/feature` или его гейты.
- Изменился шаблон промпта в `/prompt-engineer`.
- Изменилось разделение ответственности между `AGENTS.md`, скиллами и хуками.
- Переименован тип или сборка, упомянутые в тексте любого `SKILL.md`.
