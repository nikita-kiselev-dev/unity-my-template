# Tickets

## Для агента

Открывай эту статью, когда заводишь тикет, правишь его frontmatter или разбираешься, почему
`ticket-format` вернул ход. Это **единственный источник истины** по формату тикета; секция
«Тикеты / Kanban» в `AGENTS.md` — выжимка, при расхождении права у статьи.

Тикет — не задачник, а **архив решений**: через полгода к нему возвращаются с вопросом «что мы
уже решали про SaveLoad». Поэтому тикет обязан быть узлом графа vault, а не запиской: у него
есть `related:` на статью системы, предсказуемый frontmatter и предсказуемый скелет тела.

Короткий путь: скопировать канон своего `kind` (`Tasks/Features/UMT-Feature-1.md`,
`Tasks/Bugs/UMT-Bug-1.md`, `Tasks/Epics/UMT-Epic-1.md`) под следующий номер, заменить
содержимое, прогнать `powershell -File Tools/ticket-format.ps1`. Номер 1 не занимать —
это шаблон, не работа.

## Инварианты

Все проверяются машинно (`Tools/ticket-format.ps1`), кроме помеченных «глазами».

- Имя файла — `UMT-Feature-N.md`, `UMT-Bug-N.md` или `UMT-Epic-N.md`; папка соответствует типу.
- `kind` совпадает с типом из имени файла: `feature` / `bug` / `epic`.
- Обязательные поля frontmatter присутствуют и непусты: `title`, `type`, `kind`, `status`,
  `area`, `module`, `related`, `created`, `updated`, `tags`.
- `type` всегда `task` — по нему тикеты отбирает Dataview.
- `area` ∈ {`Foundation`, `Features`, `Project`, `Cross-cutting`}.
- `module` — значение из словаря `module` статей vault.
- `module` тикета совпадает с `module` хотя бы одной статьи из его `related:`.
- `related:` непустой, каждая ссылка резолвится в существующий файл vault.
- `related:` не ссылается на тикеты — для связей между тикетами есть `epic:` и `blocked_by:`.
- `tags` содержит ядро `[task, <kind>, <area-slug>, <module-slug>]`; свободные теги сверх — можно.
- Тело содержит все обязательные заголовки своего `kind`.
- `epic:` (если есть) резолвится в существующий файл `Tasks/Epics/`.
- Одновременно `In Progress` — не больше трёх тикетов `kind: feature` / `kind: bug`.
- Глазами: `related:` ведёт на статью, которая действительно про эту работу. Правдоподобная,
  но неверная связь хуже пустоты — она выглядит как факт.
- Глазами: в теле нет сгенерированных отчётов — только выводы и ссылка на файл в `.agent-state/`
  (см. «Результат прогона»).

## Именование и размещение

| Тип | Файл | Папка | Нумерация |
| --- | --- | --- | --- |
| Фича | `UMT-Feature-N.md` | `Tasks/Features/` | сквозная по фичам |
| Баг | `UMT-Bug-N.md` | `Tasks/Bugs/` | сквозная по багам |
| Эпик | `UMT-Epic-N.md` | `Tasks/Epics/` | сквозная по эпикам |

`N` — максимальный существующий номер **своего типа** плюс один. Номер 1 каждого типа —
канонический шаблон, живую задачу туда не писать. Номера не переиспользуются: отменённый
тикет остаётся файлом со `status: Cancelled`, его номер занят навсегда.

Текст тикета — на русском. Имена файлов, идентификаторы и пути — как в коде.

## Frontmatter

### Обязательные поля

| Поле | Значение | Замечание |
| --- | --- | --- |
| `title` | одна строка | без номера тикета внутри; кавычки, если есть `:` или `«»` |
| `type` | `task` | константа, по ней работает Dataview |
| `kind` | `feature` \| `bug` \| `epic` | выводится из имени файла и обязан совпасть |
| `status` | `Todo` \| `In Progress` \| `Done` \| `Cancelled` | канонический статус, доска выводится из него |
| `area` | `Foundation` \| `Features` \| `Project` \| `Cross-cutting` | закрытый список |
| `module` | из словаря статей | см. «[Словарь module](#словарь-module)» |
| `related` | список `"[[Article]]"` | непустой, только статьи |
| `created` | `YYYY-MM-DD` | дата заведения |
| `updated` | `YYYY-MM-DD` | дата последнего **содержательного** изменения: смена статуса, скоупа, критериев. Правка формата дату не двигает — иначе доска теряет хронологию |
| `tags` | список | см. «[Теги](#теги)» |

### Опциональные поля

| Поле | Значение | Когда |
| --- | --- | --- |
| `epic` | `"[[UMT-Epic-N]]"` | тикет — подтикет эпика |
| `blocked_by` | список `"[[UMT-...]]"` | работа не начинается, пока те не закрыты |

Поля `epic` и `blocked_by` — **единственный** способ сослаться из тикета на тикет во frontmatter.
`related:` для этого не используется: иначе dataview-блок статьи «Тикеты по системе» начал бы
показывать тикеты, которые к системе отношения не имеют.

### area

- `Foundation` — работа в `Assets/Framework/Foundation/`.
- `Features` — работа в `Assets/Framework/Features/`.
- `Project` — документация, тикеты, инструменты, настройки проекта, CI.
- `Cross-cutting` — работа, размазанная по слоям: тесты, интеграции, чистка обоих слоёв сразу.

`area` описывает **где велась работа**, а не где живёт система сейчас. Тикет, который перенёс
`Items` из `Foundation` в `Features`, остаётся `Cross-cutting` — переписывать его историю
задним числом смысла нет.

### Словарь module

`module` не выдумывается: это поле `module` какой-нибудь статьи vault. Актуальный словарь
получается прогоном

```bash
powershell -File Tools/ticket-format.ps1 -ListModules
```

Правило выбора: если у работы несколько модулей (`Utilities / UI / Docs`), выбирается **один
основной** — тот, чью статью откроют, чтобы понять эту работу. Остальные уходят в `related:`
дополнительными ссылками. Склейки через `/` в `module` запрещены: поле участвует в фильтрах
Dataview и в ядре `tags`, а склейка ломает и то и другое.

Если подходящей статьи нет вовсе — статья заводится. Тикет получает пункт «завести статью X» в
скоуп, а `related:` временно указывает на ближайшую по смыслу. Дыра в документации становится
работой, а не молчаливым исключением.

### Теги

Ядро обязательно и выводится из полей: `[task, <kind>, <area-slug>, <module-slug>]`.

Slug — имя в нижнем регистре, пробелы и `/` в дефис: `Cross-cutting` → `cross-cutting`,
`Assembly Boundaries` → `assembly-boundaries`, `SaveLoad` → `saveload`.

Свободные теги сверх ядра не ограничены: `refactoring`, `dataview`, `hooks`, `documentation`.

## Скелеты тела

Хук проверяет **наличие заголовков, а не содержимое**. Поэтому проверяемый набор уже, чем
шаблон: обязателен только тот заголовок, отсутствие которого означает «тикет не дописан».
Остальные заголовки шаблона нужны не меньше, но требовать их машинно бессмысленно — получишь
пустую секцию ради зелёного хука, а она хуже отсутствующей.

Ниже **жирным** — то, что проверяет `ticket-format.ps1`; обычным — то, что даёт шаблон.

### feature

| Заголовок | Что внутри |
| --- | --- |
| Цель | одно предложение: что будет уметь система после тикета |
| Проблема | блок `Сейчас / Хочу / Почему` — тот же, что даёт скилл `/feature` |
| **Скоуп** | чеклист работ; `@user`-пункты помечены маркером |
| **Критерии Done** | чем закрывается тикет; последним — `@user`-пункт приёмки |

### bug

| Заголовок | Что внутри |
| --- | --- |
| **Симптом** | что наблюдается, с `file:line` |
| Воспроизведение | шаги или тест, дающий симптом |
| Причина | корневая причина, а не место падения |
| **Решение** | что сделано; код — фрагментом |
| **Критерии Done** | чем проверяется, что баг закрыт |

### epic

| Заголовок | Что внутри |
| --- | --- |
| **Цель** | зачем эпик существует |
| **Проблема** | блок `Сейчас / Хочу / Почему` |
| **Подтикеты** | dataview по `epic:` (см. ниже) |
| **Критерии Done** | приёмка эпика целиком |

У эпика проверяется весь набор: эпиков единицы, каждый пишется с нуля, и «не дописан» тут
дороже.

Секция «Подтикеты» эпика — **dataview по `epic:`**, а не ручной список:

````markdown
```dataview
TABLE WITHOUT ID file.link AS "Подтикет", title, status, updated
FROM "Tasks"
WHERE type = "task" AND contains(string(epic), "UMT-Epic-N")
SORT file.name ASC
```
````

Ручной чеклист в эпике остаётся только для работы, **не вынесенной** в подтикеты.

## Результат прогона: выводы в тикет, данные в `.agent-state/`

Сгенерированная таблица — данные, а не текст тикета, и в теле ей не место. В тикет идут выводы:
что измерено, какие числа получились, что из них следует. Полный отчёт остаётся файлом рядом с
сырыми данными в `.agent-state/`, тикет ссылается на путь.

Вставленный в тело сгенерированный отчёт дал **288 КБ и 2768 строк в git** на тикет, который
читается за пять минут. Цена — не только размер: такой тикет невозможно просмотреть глазами,
а diff по нему бесполезен. Порог простой — если раздел **сгенерирован скриптом и растёт
с объёмом прогона**, он пишется в `.agent-state/`.

Ограничение обратной силы у него нет: `.agent-state/` в `.gitignore`, поэтому отчёт живёт только
на машине, где шёл прогон. Это сознательный размен — тикет остаётся читаемым, а воспроизводится
отчёт повторным прогоном по сырым данным.

## Чеклисты и маркер @user

Пункт, который может закрыть только пользователь (компиляция в Unity, зелёный Test Runner,
прогон сцены, настройка через Inspector, ключи вне репозитория), пишется с маркером `@user`
сразу после чекбокса:

```markdown
- [ ] @user Компиляция и зелёный Test Runner
```

Маркер — единственный машинный признак приёмки. Без него пункт считается технической работой
агента, и `acceptance-check` не будет ждать пользователя.

## Жизненный цикл

1. Тикет заводится **до** первой правки кода, ассетов или документации. Анализ, ревью и ответы
   на вопросы тикета не требуют.
2. Перед активной работой — `status: In Progress`. Одновременно активных не больше трёх.
3. Во время работы тикет держится актуальным: меняется скоуп — меняется и чеклист.
4. `Done` — только после того, как пользователь подтвердил компиляцию и результат.
5. Потерял актуальность, дубликат, оказался не багом — `Cancelled` с причиной в теле.

### Приёмка

Как только незакрытыми остались **только** `@user`-пункты, работа агента закончена. Агент
спрашивает через `AskUserQuestion` ровно двумя вариантами: «Да, всё в порядке — закрываем тикет»
и «Ещё не проверял — вернусь позже». Варианта «Нет» нет: замечания идут в штатное свободное
поле `Other` и вносятся в тикет отдельными пунктами без `@user`.

### WIP-лимит

Одновременно `In Progress` — не больше трёх тикетов `kind: feature` / `kind: bug`. Эпики в
лимит не входят: эпик живёт месяцами и активной работой не является.

Лимит существует не ради дисциплины, а ради гейта: `ticket-check` считает работу легальной,
пока хоть один тикет `In Progress`. Когда таких 22, гейт удовлетворён всегда и не ловит ничего.

## Чем это закрыто

Два скрипта, оба висят на одном Stop-хуке `Tools/hook-ticket-check.ps1`:

| Скрипт | Что проверяет | Метка повтора |
| --- | --- | --- |
| `Tools/ticket-check.ps1` | есть ли активный тикет под изменения вне `Tasks/` | `.agent-state/TicketCheck/.last-report` |
| `Tools/ticket-format.ps1` | формат тикетов: frontmatter, скелет, WIP-лимит | `.agent-state/TicketFormat/.last-report` |

Ручной прогон в середине хода:

```bash
powershell -File Tools/ticket-format.ps1 -All
```

Без ключей проверяются только тикеты, изменённые относительно `HEAD`. Есть `-Files` (явный
список), `-BaseRef` (другая база), `-ListModules` (словарь `module` статей).

Сознательное исключение — строка в `Tools/ticket-format.exceptions.txt` в формате
`<файл>:<правило> # <причина>`. Причина обязательна: строка без неё считается ошибкой скрипта,
а не разрешением.

Приёмку закрывает отдельный хук `Tools/hook-acceptance-check.ps1` — он последний в цепочке,
потому что спрашивать про приёмку имеет смысл только когда тесты, имена, доки, скоуп и тикет
чисты. Вся цепочка — [[Hooks]].

## Как добавить

### Новый тикет

1. Определить тип и взять следующий номер своего типа (не 1 — он занят шаблоном).
2. Скопировать канон (`UMT-Feature-1` / `UMT-Bug-1` / `UMT-Epic-1`), заполнить frontmatter:
   `area` из закрытого списка, `module` из словаря, `related` на статью системы.
3. Заполнить скелет тела; `@user`-пункты пометить маркером.
4. `powershell -File Tools/ticket-format.ps1` — зелёный.
5. `status: In Progress` перед началом работы.

### Новый module

Модуль появляется вместе со статьёй, а не вместе с тикетом. Порядок: завести статью (хотя бы
`status: stub` с секцией «Для агента» и `source_paths`) → добавить её в `01-Agent-Navigation.md`
и `00-Index.md` → ставить её `module` в тикеты.

### Новая статья

Любая статья vault заканчивается секцией «Тикеты по системе» — dataview-блоком, который
показывает тикеты, сославшиеся на неё через `related:`. Канонический вид блока —
в [[00-Index]], раздел «Шаблон статьи».

## Шаблоны

Канон — три файла с номером 1. Копируй целиком, не правь оригинал под живую задачу.

| kind | Файл |
| --- | --- |
| feature | `Tasks/Features/UMT-Feature-1.md` |
| bug | `Tasks/Bugs/UMT-Bug-1.md` |
| epic | `Tasks/Epics/UMT-Epic-1.md` |

Плотность, `@user`, `related:` / `module` / ядро `tags`, dataview подтикетов — смотри там.
Пустая секция ради галочки хуже отсутствующей: в каноне заполнены все заголовки скелета.

## Когда обновлять

- Меняется набор обязательных полей, допустимых `area` или правил `tags`.
- Появляется новый `kind` или новый скелет тела.
- Меняется правило `related:` или словарь `module` перестаёт браться из статей.
- Меняется WIP-лимит или состав цепочки Stop-хуков вокруг тикетов.
- `Tools/ticket-format.ps1` получает новое правило либо теряет старое.
- Меняется канон в `UMT-Feature-1` / `UMT-Bug-1` / `UMT-Epic-1`.

## Тикеты по системе

Тикеты, у которых в `related:` стоит ссылка на эту статью. Пустая таблица — сигнал: либо
система мёртвая, либо у её тикетов не проставлен `related:`.

Открытые:

```dataview
TABLE WITHOUT ID file.link AS "Тикет", title, kind, updated
FROM "Tasks"
WHERE type = "task" AND contains(string(related), "Tickets") AND (status = "Todo" OR status = "In Progress")
SORT updated DESC
```

Закрытые:

```dataview
TABLE WITHOUT ID file.link AS "Тикет", title, kind, status, updated
FROM "Tasks"
WHERE type = "task" AND contains(string(related), "Tickets") AND (status = "Done" OR status = "Cancelled")
SORT updated DESC
```
